### 2. 다중 파일 처리(Batch Processing)를 위한 파서 설정 및 Main 구동부 수정 (✅ 완료)
본격적인 타입 검사기(Type Checker)를 구현하기에 앞서, 여러 개의 MiniJava 예제 파일들을 한 번에 테스트할 수 있도록 파서의 환경과 프로그램의 진입점(`Main.java`)을 수정하였다.

**가. JavaCC 파서의 정적(Static) 옵션 해제**
기본적으로 JavaCC는 정적(Static) 파서를 생성하도록 설정되어 있다. 하지만 여러 파일을 일괄적으로 처리하기 위해 `for` 반복문 내부에서 `new MiniJavaParser(in)`를 매번 새로 인스턴스화할 경우, "Second call to constructor of static parser" 에러가 발생하게 된다. 이를 해결하기 위해 `MiniJavaParser.jj`의 `options` 블록에 `STATIC = false;` 옵션을 명시적으로 추가한 뒤 파서를 재생성하였다. 이를 통해 매 파일마다 독립적인 파서 객체를 생성하여 안전하게 파싱할 수 있게 되었다.

**나. Main.java 다중 파일 처리 로직 구현**
파서 설정을 변경한 뒤, `Main.java`를 수정하여 터미널을 통해 입력받은 모든 파일 경로(`args`)를 `for`문으로 순회하도록 구현하였다. 
현재는 타입 검사기 방문자(Visitor)가 구현되기 전이므로, 우선 `root.accept(new PrettyPrintVisitor())`를 통해 구문 트리가 정상적으로 빌드되었는지 테스트하였다. 향후 기호 테이블과 타입 검사 방문자가 완성되면, 해당 부분을 주석 해제하여 일괄적인 타입 검사 결과를 출력(`Successfully type checked for...` 등)하도록 확장 가능한 구조를 마련하였다. 전체 8개의 예제 프로그램에 대해 일괄 테스트를 진행한 결과, 파싱 단계에서 아무런 오류 없이 정상 구동됨을 확인하였다.

### 3. 기호 테이블 (Symbol Table) 자료구조 설계 (✅ 완료)
MiniJava의 타입 검사를 위한 기호 테이블(Symbol Table)의 자료구조를 설계하였다.
교재(Modern Compiler Implementation in Java)의 5.1절에서는 범용 컴파일러를 위한 별도의 패키지 구조를 제안하지만, 컴파일러의 실용성과 자동화된 테스트(TDD)를 고려하여 교수님의 강의 자료에 제시된 최적화된 레퍼런스 구현 구조를 채택하였다.
- 별도의 외부 클래스를 만들지 않고 **`TypeCheckVisitor` 클래스 내부에 정적 중첩 클래스(Static Nested Class)로 `ClassInfo`와 `MethodInfo`를 정의**하였다. 
- 변수 메타데이터는 AST의 `syntaxtree.Type` 객체를 그대로 Value로 사용하였으며, 식별자 이름(`String`)을 Key로 하는 자바의 기본 `HashMap`과 메서드 파라미터의 순서를 보장하기 위한 `LinkedHashMap`을 활용하였다.

### 4. 2-Pass 순회 및 에러 처리(Error Handling) 구조 구현 (✅ 완료)
MiniJava는 선언 순서와 무관하게 클래스나 메서드를 참조할 수 있는 **전방 참조(Forward Reference)** 를 허용하므로, 1-Pass(단일 순회)로는 타입 검사가 불가능하다. 
- 이를 해결하기 위해 `TypeCheckVisitor` 내부에 `Phase` enum (COLLECT, CHECK)을 두어, 1차 순회에서는 기호만 수집하고 2차 순회에서 실제 타입 검사를 수행하는 **2-Pass 순회 구조**를 확립하였다.
- 또한 파싱 단계와 달리 의미 분석 단계에서는 에러를 발견해도 즉시 종료하지 않고 모든 에러를 수집해야 한다. 순회 중 발견된 에러는 `error(String msg)` 메서드를 통해 `ArrayList<String> errors`에 누적만 해 두고, 2차 순회가 모두 끝난 직후 `check()` 메서드의 마지막 단계에서 누적된 모든 에러들을 콘솔(`System.err.println`)에 일괄 출력하도록 구현하였다. 부가적으로 `Main.java`에서 검증을 수행하기 위해 에러 리스트를 반환하는 `getErrors()` 메서드를 열어두어, 특정 파일에서 의도한 개수만큼 에러가 발생하는지 TDD 방식으로 테스트할 수 있도록 하였다.

### 5. 기호 테이블 데이터 삽입 헬퍼 메서드 구현 (✅ 완료)
AST 순회 중 기호를 안전하게 테이블에 저장하기 위해, 각 스코프(Scope)를 담당하는 클래스 성격에 맞추어 전용 헬퍼 메서드를 세분화하여 구현하였다.

- **`TypeCheckVisitor` 내부의 `addClass`**: 전역 스코프를 관리하므로, 전체 프로그램의 클래스 이름들을 `classes` 맵에 등록하고 중복 선언을 검사한다.
- **`ClassInfo` 내부의 `addVar`, `addMethod`**: 단일 클래스 스코프를 담당하므로, 해당 클래스 내부에 선언되는 필드 변수(`addVar`)와 메서드(`addMethod`)를 각각의 `HashMap`에 등록하며 클래스 내 중복 선언을 차단한다.
- **`MethodInfo` 내부의 `addParam`, `addLocal`**: 단일 메서드 스코프를 담당한다. 공식 타입 명세서(7.5절)의 `distinct` 수식에 따라 파라미터와 지역 변수 간의 이름 중복이 엄격히 금지되므로, `addLocal` 내부에서는 기존의 `params`와 `locals` 맵 양쪽을 모두 검사하도록 견고하게 구현하였다.

이 헬퍼 메서드들은 이름 충돌이 발생할 경우 즉시 `false`를 반환하여, 호출부(Visitor)에서 즉각적인 `error()` 출력을 유도할 수 있도록 설계되었다.

### 6. TDD(테스트 주도 개발)를 위한 자동 검증 환경 및 테스트 파일 구축 (✅ 완료)
본격적인 `visit` 오버라이드 및 기호 수집에 앞서, 점진적 구현(TDD)을 위한 환경을 구축하였다.
- **`TypeVisitor` 인터페이스 뼈대 완비**: 자바의 엄격한 인터페이스 규약으로 인한 컴파일 에러를 해결하기 위해, `TypeVisitor`가 요구하는 모든 AST 노드 순회용 `visit` 메서드들의 빈 껍데기(Dummy Shell)를 `TypeCheckVisitor`에 오버라이드하여 정상적으로 빌드가 가능한 상태를 확보하였다.
- **실패 케이스 테스트 파일(`TestDuplicate.java`) 작성**: 교수님 슬라이드에 제시된 이름 중복 에러 케이스들을 모아, ①중복 필드 변수, ②중복 지역 변수, ③파라미터와 이름이 겹치는 지역 변수, ④중복 메서드, ⑤중복 클래스 등 **총 5개의 의도적인 이름 충돌 에러**를 포함하는 전용 테스트 파일을 작성하였다. (향후 선언되지 않은 변수 사용 에러나 타입 불일치를 검증하기 위한 `TestUndeclared.java`, `TestTypeMismatch.java` 등도 단계적으로 추가할 예정이다.)
- **`Main.java` 내 자동 검증(Assertion) 로직 추가**: 여러 파일을 일괄 검사하는 `Main.java`에 로직을 추가하여, `TestDuplicate.java`를 검사할 때는 `typeChecker.getErrors().size() == 5` 조건을 검사하도록 하였다. 이를 통해 우리가 의도한 5개의 에러를 정확히 모두 잡아낼 경우에만 `TDD PASS`를 출력하게 하여, 향후 에러를 하나씩 격파해 나가는 TDD 기반의 자동 채점 환경을 완성하였다.

### 7. Phase 1(COLLECT 단계) 기호 수집 및 자바 표준 에러 메시지 구현 (✅ 완료)
본격적인 타입 검사에 앞서 `TypeCheckVisitor`의 1차 순회(Phase.COLLECT) 로직을 완성하여 `TestDuplicate.java`에 심어둔 5가지 에러를 모두 완벽히 격파하였다.
- **클래스 및 변수/메서드 스코프 수집**: `visit(Program)`, `visit(MainClass)`, `visit(ClassDeclSimple)`, `visit(ClassDeclExtends)`를 오버라이드하여 전역 스코프에 클래스를 수집하였다. 또한 `visit(MethodDecl)`, `visit(VarDecl)`, `visit(Formal)`을 통해 각 클래스와 메서드 내부의 변수 및 파라미터들을 Symbol Table(`ClassInfo`, `MethodInfo`)에 재귀적으로 저장하도록 구현하였다.
- **자바 컴파일러(`javac`) 수준의 정교한 에러 메시지 구현**: 중복 선언 에러 발생 시 출력되는 메시지를 실제 자바 컴파일러와 99% 동일한 포맷으로 오마주(Hommage)하였다. 특히, 메서드 내부의 지역 변수나 파라미터 중복 시 단순 메서드 이름뿐만 아니라 `ComputeFac(int)`와 같이 파라미터 타입이 포함된 완벽한 시그니처를 출력하도록 `MethodInfo` 내부에 `getSignature()` 헬퍼 메서드를 추가하였다. 이를 통해 과제 수준을 넘어선 매우 친절하고 상용 컴파일러에 가까운 에러 리포팅 시스템을 구축하였다.

### 8. Phase 2(CHECK 단계) 미선언 식별자 검출 로직 및 AST 순회 오류 해결 (✅ 완료)

기호 수집이 완료된 심볼 테이블을 바탕으로 `TypeCheckVisitor`의 2차 순회(Phase.CHECK)를 구현하여, 전방 참조(Forward Reference)를 포함한 식별자 참조 유효성을 엄밀하게 검증하였다. 구현에 앞서 테스트 주도 개발(TDD) 방법론에 입각하여, 미선언 클래스 상속(`extends`), 미선언 객체 생성(`new`), 잘못된 식별자를 이용한 대입문(`a = b`) 등 발생 가능한 모든 엣지 케이스를 포함하는 `TestUndeclared.java`를 작성하였으며, 총 7개의 에러를 정확히 포착하도록 자동화된 검증 환경을 고도화하였다.

본격적인 식별자 검출 로직을 위해, 참조가 발생할 때마다 현재 문맥의 스코프 체인(Scope Chain)을 동적으로 추적하는 `getVarType` 헬퍼 메서드를 고안하였다. 이 메서드는 참조된 변수를 찾기 위해 '현재 메서드의 지역 변수 ➡ 파라미터 ➡ 현재 속한 클래스의 필드 ➡ 상속된 부모 클래스의 필드' 순으로 심볼 테이블을 상향식(Bottom-Up)으로 탐색하며, 유효하지 않은 식별자 참조를 원천 차단한다.

또한, 변수나 객체 생성 코드가 숨어있을 수 있는 조건문(`If`), 반복문(`While`), 메서드 호출(`Call`), 사칙연산(`Plus` 등)과 같은 모든 수식 및 구문 노드 내부에도 자식 노드를 방문하는 `accept(this)` 호출을 추가하였다. 1차 순회(COLLECT) 단계에서는 탐색을 생략했던 이 노드들을 2차 순회에서 끝까지 파고들어 검사함으로써, 코드 깊숙한 곳에 숨겨진 미선언 변수(`IdentifierExp`)나 클래스(`NewObject`) 참조 오류를 빠짐없이 잡아낼 수 있게 되었다. 이렇게 검출된 모든 미선언 오류는 실제 자바 컴파일러와 동일하게 `cannot find symbol: variable/class`라는 직관적인 메시지로 출력되도록 다듬었다.

### 9. Phase 3(CHECK 단계) 메서드 오버로딩(Overloading) 원천 차단 (✅ 완료)

미니자바(MiniJava)의 엄격한 타입 시스템 명세(Rule 6.8 `noOverloading`)를 준수하기 위해, 자식 클래스에서 부모 클래스의 메서드와 동일한 이름으로 파라미터나 리턴 타입을 변형하여 재정의하는 오버로딩 시도를 전면 차단하였다. 이를 위해 `TestOverload.java`를 작성하여 리턴 타입 변경, 파라미터 개수 변경, 파라미터 타입 변경, 다중 파라미터 타입 변경, 그리고 조부모 클래스 메서드에 대한 오버로딩 시도까지 총 5가지의 불법적 엣지 케이스를 선제적으로 구축하였다. (반면 완벽히 동일한 시그니처를 가진 합법적 오버라이딩은 통과하는 것까지 검증하였다.)

실제 AST 순회 과정에서 이 규칙을 강제하기 위해, 먼저 두 `Type` 객체의 완전한 일치 여부를 검사하는 `isSameType` 헬퍼 메서드를 추가하였다. 이 메서드는 `int`나 `boolean` 같은 기본형 타입뿐만 아니라, `IdentifierType` 객체의 내부 문자열(사용자 정의 클래스 이름)까지 정밀하게 비교하여 타입 동치성을 판별한다. 
이후 2차 순회(CHECK)의 `visit(MethodDecl)` 진입 시 `checkOverloading` 로직을 발동시켜 오버로딩 여부를 검증한다. 이 로직은 `while (parentClass != null)` 루프를 통해 현재 클래스의 직계 부모를 넘어 조부모 클래스까지 상향식(Bottom-Up)으로 상속 계층을 모두 거슬러 올라가며 동일한 이름의 메서드가 존재하는지 탐색한다.
만약 상위 클래스에서 이름이 같은 메서드를 발견할 경우, 다음 세 가지 시그니처 조건을 엄격하게 검사한다:
1) 두 메서드의 리턴 타입이 `isSameType`을 만족하는가
2) 파라미터의 총개수가 동일한가
3) `Iterator`를 활용해 파라미터 목록을 순회하며, 순서대로 각 자리의 파라미터 타입이 1:1로 정확히 일치하는가
위 조건 중 단 하나라도 불일치할 경우, 합법적인 오버라이딩(Overriding)이 아닌 불법적인 오버로딩(Overloading) 시도로 간주하고 즉각적으로 `method ... illegally overloads method in class ...` 포맷의 에러를 발생시킴으로써 미니자바의 제약 사항을 완벽하게 구현해 내었다.

### 10. Phase 4(CHECK 단계) 상속 트리 순환 오류 차단 (Acyclic 제약) (✅ 완료)

미니자바 명세서의 Rule 6.5(`acyclic` 규칙)에 따라, 클래스 상속 관계가 꼬여서 무한 루프(순환 상속)에 빠지는 것을 방지하는 로직을 구현하였다. 이를 검증하기 위해 `TestAcyclic.java` 테스트 코드를 작성하고, 자기 자신을 상속(`A extends A`), 인접한 두 클래스 간의 교차 상속(`B extends C`, `C extends B`), 그리고 세 클래스가 꼬리를 무는 간접 순환 상속(`D->E->F->D`) 등 총 6가지의 순환 상속 에러 케이스를 배치하였다.

순환 상속을 탐지하기 위해 `TypeCheckVisitor`의 2차 순회(CHECK)의 `visit(ClassDeclExtends)` 단계에서 동작하는 `checkAcyclic` 헬퍼 메서드를 추가하였다. 이 메서드는 현재 클래스를 시작점으로 삼아, `while` 루프를 돌며 부모, 조부모 클래스를 순차적으로 거슬러 올라간다. 이때 `HashSet<String>` 자료구조를 수첩처럼 활용하여 지금까지 방문한 모든 조상 클래스의 이름을 저장해 둔다. 만약 부모를 타고 올라가다가 이미 `HashSet`에 저장된 이름을 다시 마주치게 되면, 상속 족보가 꼬여 루프가 발생했다고 판단하고 즉각 탐색을 중단한다. 그리고 실제 자바 컴파일러(`javac`)와 완전히 동일한 포맷인 `cyclic inheritance involving class ...` 에러를 발생시켜 잘못된 상속을 깔끔하게 차단하였다.

### 11. Phase 5-1(CHECK 단계) 수식(Expression) 타입 반환 및 인자 검사 (✅ 완료)

미니자바 명세서의 수식(Expression) 타입 규칙들을 완벽하게 준수하기 위해, 평가 결과로 반드시 특정 타입(Type)을 반환해야 하는 AST 노드들의 검사 로직을 구현하였다. 이를 위해 `TestExprMismatch.java`를 작성하여 `int + boolean`, `!int`, 배열이 아닌 변수에 대한 인덱스 접근(`arr[false]`), 메서드 인자 개수 및 타입 불일치, 존재하지 않는 메서드 호출(`unknownMethod()`) 등 수식 계산 과정에서 발생할 수 있는 14가지의 치명적인 타입 에러 케이스를 배치하였다.

수식 검사 로직의 핵심은 각 `visit` 메서드가 자식 노드를 순회한 후 그 결과 타당성을 검증하고 자신의 타입을 상위 노드로 리턴(`return new IntegerType();` 등)하는 것이다.
특히 메서드 호출(`Call`) 노드의 경우 미니자바에서 가장 복잡한 5단계의 검사 로직을 도입하였다. 
1) 호출 대상 객체의 타입을 구하고 클래스인지 확인한다.
2) `getMethod` 헬퍼 메서드를 통해 상속 계층(족보)을 거슬러 올라가며 해당 메서드가 존재하는지 찾는다(없으면 즉각 에러 발생).
3) 파라미터 개수의 일치 여부를 검사한다.
4) 런타임 다형성을 지원하기 위해, 새롭게 고안한 `isSubtype` 헬퍼 메서드를 사용하여 전달된 인자(Argument)의 타입이 선언된 파라미터(Parameter)의 하위 타입인지를 엄격하게 검증한다.
이러한 체계적인 검사를 통해 총 14개의 수식 에러 덫을 컴파일러가 모두 정확하게 밟고 에러를 리포팅하는 것을 확인하였다.

### 12. Phase 5-2(CHECK 단계) 구문(Statement) 흐름 제어 및 대입 타입 검사 (✅ 완료)

수식과 달리 실행 흐름만을 제어하고 타입을 반환하지 않는 구문(Statement) 노드들에 대한 타입 규칙을 구현하였다. 이를 위해 `TestStmtMismatch.java`를 분리 작성하여, 조건문에 `int` 사용(`if(1)`, `while(1)`), `boolean`을 `Print`로 출력 시도, 호환되지 않는 클래스 간의 대입(`objC = objA`), 그리고 메서드의 선언된 리턴 타입과 실제 리턴하는 값의 타입 불일치(`return true;`) 등 7가지의 제어 흐름 및 대입 에러 케이스를 구축하였다.

구문 타입 검사 로직은 AST를 순회하며 `return null;`을 유지하되, 내부 조건식이나 대입식의 합법성만을 강하게 제약한다.
- **제어문(`If`, `While`)**: 조건식 노드(`n.e.accept(this)`)가 반환한 타입이 반드시 `BooleanType`인지 검사한다.
- **대입문(`Assign`, `ArrayAssign`)**: 심볼 테이블에서 좌항(LHS) 식별자의 선언 타입을 `getVarType`으로 가져온 뒤, 우항(RHS) 수식의 평가 결과 타입이 좌항의 서브타입(Subtype)인지를 `isSubtype` 메서드로 검사하여 불법적인 객체 대입을 차단한다.
- **메서드 리턴(`MethodDecl`)**: 메서드 선언부에 명시된 리턴 타입과, `return` 키워드 뒤에 오는 수식의 최종 반환 타입이 서브타이핑 관계를 만족하는지 검사한다.
결과적으로 `TestStmtMismatch.java`의 7가지 에러를 모두 완벽히 잡아내며, 수식부터 구문까지 빈틈없이 이어지는 21개의 철벽 타입 체커(Type Checker) 개발이 최종 완료되었다.
